# PitchZone — полная спецификация продукта

Этот файл — единый источник правды о проекте. Отдавай его целиком AI-агенту (Cursor/Claude Code) в начале работы и держи прикреплённым/открытым во всех последующих сессиях, чтобы контекст не терялся. Файл описывает: сущности данных, все пользовательские сценарии, статусы/переходы, API, платежи, роли, дизайн и техстек.

---

## 1. Что это за продукт

PitchZone — платформа для организации и проведения турниров по киберфутболу (EA FC, eFootball и т.п.), где игроки и команды платят взнос за участие, а платформа удерживает комиссию с призового фонда. Деньги участников хранятся в эскроу до завершения турнира и автоматически распределяются победителям.

## 2. Роли пользователей и права на создание турниров

| Роль                                       | Права                                                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Guest**                                  | просмотр публичных турниров и статистики без регистрации                                                                                                     |
| **Player**                                 | регистрируется, вступает в турниры/команды, играет матчи, имеет кошелёк, **может создавать только закрытые (приватные) турниры**                             |
| **Team Captain**                           | то же, что Player + управляет составом команды, регистрирует команду на сезоны и открытые турниры                                                            |
| **Organizer (public tournaments granted)** | обычный пользователь, которому **администратор точечно выдал право создавать открытые (публичные) турниры** — см. 4.3.1                                      |
| **Moderator**                              | разбирает споры (disputes), банит читеров, модерирует контент, ведёт статистику матчей (StatTracker)                                                         |
| **Admin**                                  | полный доступ: финансы, настройка комиссий, управление ролями/правами, аналитика, **единственный, кто может создавать и вести сезоны платформы (раздел 11)** |

### 2.1 Важное разделение: три уровня турниров

На платформе принципиально разные права на разные типы турниров — это нужно закладывать в модель прав с самого начала:

1. **Сезоны платформы (Season)** — главные, официальные турниры платформы (см. раздел 11: Осень-зима / Зима-весна / Весна-лето, дивизионы Золото/Серебро/Бронза, годовой отбор на LAN). **Создаёт и ведёт исключительно администратор.** Никакая другая роль не может создать или редактировать `Season`. Это ядро продукта и основной источник дохода/удержания аудитории — контроль над ним не делегируется.
2. **Открытые (публичные) турниры вне сезонов** — обычные турниры с публичным листингом (например, разовые кубки, аналог "еженедельного кубка" из раздела 11.1). Создавать их может либо сам админ, либо обычный пользователь, **которому админ явно выдал право `can_create_public_tournaments`** (см. 4.3.1). Без этого права кнопка создания публичного турнира пользователю недоступна в интерфейсе.
3. **Закрытые (приватные) турниры** — доступны **любому зарегистрированному пользователю без специальных прав** (см. раздел 4.10) — например, "матч на деньги" между двумя своими командами, кастомные турниры внутри сообщества и т.п. Не попадают в общий публичный листинг, доступны только по прямой ссылке/приглашению. Платформа всё равно берёт комиссию с призового фонда таких турниров.

## 3. Модель данных (основные сущности)

### User

```
id, email, password_hash (или oauth_provider/oauth_id), nickname, avatar_url,
country, role (player/moderator/admin),
can_create_public_tournaments (bool, default false — выдаётся вручную админом, см. 4.3.2),
elo_rating (default 1000), is_verified (bool),
created_at, updated_at
```

### OrganizerApplication

```
id, user_id (-> User), motivation_text, community_links (JSON),
status (PENDING / APPROVED / REJECTED), reviewed_by (-> Admin), reviewed_at,
created_at
```

### Team

```
id, name, logo_url, captain_id (-> User),
elo_rating, created_at
```

### TeamMember

```
id, team_id (-> Team), user_id (-> User), role (captain/member), joined_at
```

### Tournament

```
id, organizer_id (-> User), title, description, banner_url, game (EA_FC / EFOOTBALL / OTHER),
format (SINGLE_ELIM / DOUBLE_ELIM / ROUND_ROBIN / SWISS),
match_format (BO1 / BO3 / BO5), team_size (1 for 1v1, 5 for 5v5, 11 for 11v11),
max_participants, entry_fee (decimal, nullable = free),
currency, prize_pool_type (FROM_FEES / FIXED_SPONSORED),
fixed_prize_pool (decimal, nullable),
prize_distribution (JSON: [{place:1, percent:50}, {place:2, percent:30}, {place:3, percent:20}]),
platform_commission_percent (decimal),
registration_deadline, start_at,
rules_text, proof_requirement (SCREENSHOT / VIDEO / BOTH),
status (DRAFT / PENDING_MODERATION / REGISTRATION_OPEN / REGISTRATION_CLOSED /
         BRACKET_GENERATED / LIVE / FINISHED / CANCELLED),
visibility (PUBLIC / PRIVATE),
created_at, updated_at
```

### TournamentParticipant

```
id, tournament_id, participant_type (USER / TEAM), user_id (nullable), team_id (nullable),
seed_number, payment_status (PENDING / PAID / REFUNDED),
registered_at
```

### Bracket / Match

```
id, tournament_id, round_number, match_number_in_round,
participant_a_id, participant_b_id (nullable для bye),
status (SCHEDULED / IN_PROGRESS / AWAITING_CONFIRMATION / COMPLETED / DISPUTED / CANCELLED),
score_a, score_b,
score_reported_by_a (bool), score_reported_by_b (bool),
proof_url_a, proof_url_b,
winner_id (nullable), scheduled_at, completed_at,
next_match_id (-> Match, для продвижения победителя по сетке)
```

### Dispute

```
id, match_id, opened_by (-> User), reason_text, evidence_urls (array),
status (OPEN / UNDER_REVIEW / RESOLVED_A / RESOLVED_B / REJECTED),
resolved_by (-> Moderator), resolution_note, created_at, resolved_at
```

### Wallet

```
id, user_id (-> User), balance (decimal), currency, updated_at
```

### Transaction

```
id, wallet_id, type (DEPOSIT / ENTRY_FEE_HOLD / ENTRY_FEE_REFUND /
       PRIZE_PAYOUT / PLATFORM_COMMISSION / WITHDRAWAL),
amount, related_tournament_id (nullable), related_match_id (nullable),
status (PENDING / COMPLETED / FAILED),
external_payment_id (Stripe/etc reference), created_at
```

### EscrowAccount (по турниру)

```
id, tournament_id, total_held (decimal), status (HOLDING / DISTRIBUTED / REFUNDED)
```

### Notification

```
id, user_id, type (MATCH_STARTING / TOURNAMENT_REGISTRATION_CLOSING /
     PRIZE_RECEIVED / DISPUTE_UPDATE / TOURNAMENT_CANCELLED),
payload (JSON), is_read (bool), created_at
```

## 4. Полные пользовательские сценарии

### 4.1 Регистрация и профиль

1. Пользователь регистрируется через email/пароль либо OAuth (Discord, Steam).
2. Заполняет никнейм, страну, аватар.
3. Стартовый Elo-рейтинг = 1000.
4. Профиль публично показывает: рейтинг, историю матчей (W/L), текущие турниры, достижения (значки за призовые места).

### 4.2 Создание команды

1. Игрок создаёт команду → становится капитаном.
2. Капитан приглашает других игроков по нику/ссылке.
3. Приглашённый подтверждает вступление.
4. Командный Elo = среднее/агрегат рейтингов участников (пересчитывается после каждого матча).

### 4.3 Создание турнира (мастер из 5 шагов)

#### 4.3.1 Кто может нажать «Создать турнир» и что ему доступно

- **Обычный пользователь без прав** видит в мастере создания только опцию **«Закрытый турнир»** (visibility принудительно = `PRIVATE`, шаг «Публикация» пропускается — турнир становится доступен сразу по ссылке, без модерации).
- **Пользователь с флагом `can_create_public_tournaments = true`** дополнительно видит опцию **«Открытый турнир»** — публичный листинг, попадает в общую афишу турниров на главной странице.
- **Администратор** видит обе опции всегда, плюс отдельный, полностью самостоятельный раздел «Сезоны» (раздел 11) — сезоны создаются не через этот мастер турниров, а через отдельный админский интерфейс, так как это принципиально другая сущность (`Season`, а не `Tournament`).

#### 4.3.2 Флоу выдачи права на публичные турниры

1. Пользователь, у которого пока нет права `can_create_public_tournaments`, может подать заявку из личного кабинета («Подать заявку на статус организатора») — короткая форма: опыт проведения турниров, ссылки на сообщество/канал, зачем нужны публичные турниры.
2. Заявка попадает в очередь модерации в админ-панели (`OrganizerApplication`, статус `PENDING`).
3. Администратор одобряет или отклоняет вручную. При одобрении — на `User` выставляется `can_create_public_tournaments = true`, пользователю приходит уведомление.
4. Право можно отозвать в любой момент из админ-панели (например, при злоупотреблениях) — тогда все уже созданные этим пользователем открытые турниры, которые ещё не стартовали, переводятся в статус `PENDING_MODERATION` для проверки админом, а не удаляются автоматически.

#### 4.3.3 Сам мастер создания (шаги формы)

**Шаг 1 — Основное**: название, описание, баннер, игра, дата старта, дедлайн регистрации.

**Шаг 2 — Формат**: тип сетки, число участников (степень двойки для elimination: 4/8/16/32/64), Bo1/Bo3/Bo5, 1v1 или командный формат и размер команды.

**Шаг 3 — Деньги**:

- Если `prize_pool_type = FROM_FEES`: организатор указывает `entry_fee`, призовой фонд считается автоматически = `entry_fee × max_participants × (1 - platform_commission_percent)`.
- Если `FIXED_SPONSORED`: организатор указывает фиксированный приз, участие может быть бесплатным или с меньшим взносом.
- Указывается разбивка призовых по местам (валидация: сумма процентов = 100%).

**Шаг 4 — Правила**: текст регламента, требование к пруфу результата (скриншот/видео/оба), правила дисквалификации за читерство.

**Шаг 5 — Публикация**: превью карточки турнира → кнопка "Опубликовать".

- Закрытый турнир → публикуется сразу, без модерации, доступен только по ссылке (4.10).
- Открытый турнир от пользователя с правом `can_create_public_tournaments` → уходит в `PENDING_MODERATION`, админ подтверждает перед появлением в публичном листинге (даже при наличии права — лёгкая модерация остаётся как страховка от спама/мошенничества).
- Открытый турнир от самого админа → публикуется сразу.

### 4.4 Регистрация участника на турнир

1. Пользователь/капитан команды на странице турнира жмёт "Участвовать".
2. Если `entry_fee > 0`: открывается платёжная форма (Stripe/локальный провайдер) → деньги списываются и переводятся в `EscrowAccount` турнира со статусом `HOLDING`, создаётся `Transaction` типа `ENTRY_FEE_HOLD`.
3. Создаётся `TournamentParticipant` с `payment_status = PAID`.
4. Если участников набралось `max_participants` до дедлайна — регистрация закрывается автоматически (`status = REGISTRATION_CLOSED`).
5. Если к дедлайну набралось меньше минимального порога (настраивается, напр. < 4) — турнир отменяется, всем участникам возвращаются деньги (`Transaction: ENTRY_FEE_REFUND`), статус `CANCELLED`.

### 4.5 Генерация сетки

1. По закрытии регистрации система генерирует `Bracket`/`Match` записи.
2. Посев (seeding): случайный либо по Elo-рейтингу (сильные разводятся по разным половинам сетки).
3. Организатор может вручную скорректировать посев до нажатия "Начать турнир".
4. `Tournament.status = LIVE`, первые матчи получают `status = SCHEDULED`.

### 4.6 Проведение матча

1. Матч переходит в `IN_PROGRESS`, когда наступает `scheduled_at` (или вручную по кнопке "Начать матч").
2. Игроки играют матч в самой игре (EA FC/eFootball) — платформа не хостит геймплей, только фиксирует результат.
3. Каждая сторона вводит счёт + загружает пруф (скриншот/видео) в объектное хранилище (S3/R2).
4. Логика сверки:
   - Если `score_a` от обеих сторон совпадает → `status = COMPLETED`, определяется `winner_id`, победитель автоматически продвигается в `next_match_id`.
   - Если счета не совпадают или одна из сторон не вводит результат за N часов (таймаут, настраивается) → `status = DISPUTED`, создаётся запись `Dispute`.
5. Проигравший выбывает (single elimination) либо уходит в нижнюю сетку (double elimination) либо продолжает участвовать в оставшихся турах (round robin/swiss).

### 4.7 Разрешение спора (Dispute)

1. Модератор видит очередь споров в админ-панели, открывает пруфы обеих сторон.
2. Может запросить дополнительные доказательства (видео повторной записи, встроенная статистика игры).
3. Выносит решение: `RESOLVED_A` / `RESOLVED_B` (кто-то признаётся победителем) либо `REJECTED` (переигровка матча).
4. Match обновляется соответствующим статусом, турнир продолжается.

### 4.8 Завершение турнира и выплаты

1. Когда финальный матч получает `COMPLETED` — `Tournament.status = FINISHED`.
2. Система рассчитывает призовые по `prize_distribution` от общей суммы в `EscrowAccount`.
3. Комиссия платформы (`platform_commission_percent`) списывается отдельной транзакцией `PLATFORM_COMMISSION` на системный счёт.
4. Оставшаяся сумма зачисляется на `Wallet` победителей соответствующих мест (`Transaction: PRIZE_PAYOUT`).
5. `EscrowAccount.status = DISTRIBUTED`.
6. Игроки получают уведомление `PRIZE_RECEIVED`.
7. Elo-рейтинг всех участников пересчитывается по итогам турнира (система рейтинга — например, модификация Elo с учётом занятого места, не только W/L отдельных матчей).

### 4.9 Вывод средств

1. Пользователь в разделе "Кошелёк" видит баланс и историю транзакций.
2. Жмёт "Вывести" → указывает сумму и способ (карта/локальный провайдер) → создаётся `Transaction: WITHDRAWAL` со статусом `PENDING`, отправляется запрос в платёжный провайдер (Stripe Connect payout / аналог).
3. По завершении обработки статус меняется на `COMPLETED` либо `FAILED` (с указанием причины и авто-возвратом на баланс).

### 4.10 Приватные турниры между командами (доп. монетизация)

1. Обычный пользователь (не верифицированный организатор) может создать приватный турнир (`visibility = PRIVATE`) — например, "матч на деньги" между двумя конкретными командами.
2. Такой турнир не отображается в общем листинге, доступен только по прямой ссылке/приглашению.
3. Платформа всё равно берёт комиссию с призового фонда (даже с приватных турниров) — это отдельный источник дохода.

### 4.11 Отмена турнира

1. Организатор может отменить турнир до старта (`status != LIVE`).
2. Всем оплатившим участникам автоматически возвращаются деньги (`ENTRY_FEE_REFUND`).
3. Уведомление `TOURNAMENT_CANCELLED` всем участникам.

## 5. Диаграмма статусов (текстовое описание жизненного цикла)

**Tournament:**
`DRAFT → (PENDING_MODERATION →)? REGISTRATION_OPEN → REGISTRATION_CLOSED → BRACKET_GENERATED → LIVE → FINISHED`
(альтернативная ветка: `→ CANCELLED` на любом этапе до `LIVE`)

**Match:**
`SCHEDULED → IN_PROGRESS → AWAITING_CONFIRMATION → COMPLETED`
(альтернативная ветка: `AWAITING_CONFIRMATION → DISPUTED → COMPLETED` после решения модератора)

**Transaction (для взноса):**
`ENTRY_FEE_HOLD (PENDING → COMPLETED)` → в конце турнира либо `PRIZE_PAYOUT`, либо (если турнир отменён) `ENTRY_FEE_REFUND`

## 7. Дизайн-система (кратко)

- Тёмная тема, фон `#0B0D12`, акцент `#C6FF3D` (лайм) или `#3DE7FF` (циан).
- Заголовки: Space Grotesk (жирный), текст: Inter.
- Компоненты: Card (турнир), BracketNode (матч в сетке — с состояниями по цвету: серый=scheduled, жёлтый=in_progress, зелёный=completed, красный=disputed), StatCard (профиль/рейтинг), Countdown (до старта турнира).

## 8. Технический стек

**Frontend:** Next.js 14+ (App Router), TypeScript, Tailwind CSS, shadcn/ui, Framer Motion, Zustand/React Query, Socket.io-client.

**Backend:** NestJS (TypeScript), PostgreSQL (Prisma ORM), Redis (кэш/очереди/live-статусы), Socket.io/ws сервер, BullMQ для фоновых задач (расчёт призовых, авто-старт матчей по расписанию, отправка уведомлений).

**Платежи:** Stripe Connect (эскроу через Stripe: удержание на платформенном балансе, разделение выплат — split payments/transfers), + локальный провайдер по необходимости.

**Хранилище файлов:** S3-совместимое (Cloudflare R2) — для пруфов матчей и баннеров.

**Инфраструктура:** Docker, GitHub Actions (CI/CD), Sentry (ошибки), Grafana+Prometheus (метрики), Railway/Render/Fly.io для старта, Kubernetes при росте нагрузки.

**Auth:** Auth.js/NextAuth или Clerk, OAuth Discord + Steam.

## 11. Модуль сезонов и дивизионов (режим «Клубы 11 на 11»)

Важное уточнение по продукту: платформа фокусируется **только на режиме «Клубы 11 на 11»** (командный режим EA FC), как и у референса. Весь модуль ниже описывает именно эту механику лиги/сезонов — это то, что отличает продукт от разового турнирного сервиса и превращает его в постоянно живое комьюнити.

### 11.0 Кто управляет сезонами

Напоминание из раздела 2.1: **создание, настройка и ведение `Season` — исключительное право администратора**, отдельное от обычного мастера создания турниров (раздел 4.3). У админа в панели отдельный раздел «Сезоны платформы» с CRUD для `Season`/`Division`, назначением `PromotionRelegationRule` и запуском расчёта `AnnualStanding`. Пользователи (даже с правом `can_create_public_tournaments`) не видят кнопку создания сезона — только подачу заявки команды на уже созданный админом сезон (флоу 11.5).

### 11.1 Календарь сезонов

Три официальных сезона в год, формирующих командный рейтинг:

| Сезон      | Период            |
| ---------- | ----------------- |
| Осень-зима | октябрь – декабрь |
| Зима-весна | январь – март     |
| Весна-лето | апрель – июнь     |

Летом (июнь–август, между сезонами) — отдельный **развлекательный турнир** (по типу "офсезонного кубка"), где командам разрешено микшировать составы, приглашать гостевых игроков, экспериментировать — рейтинг за него не начисляется.

Каждую неделю (например, по пятницам) — **регулярный еженедельный кубок**, открытый для всех желающих, вне рамок сезона: часть команд использует его для просмотра новых игроков (скаутинг), часть — просто ради игры. Тоже без влияния на официальный рейтинг.

### 11.2 Структура дивизионов

- **Первый сезон платформы**: дивизионов нет — все зарегистрированные команды играют в одной общей группе/сетке. Это точка входа для нового комьюнити.
- **Со второго сезона**: по итогам предыдущего сезона (место в таблице/рейтинг очков) команды распределяются по трём дивизионам:
  - 🥇 **Золотая лига** — топ-команды
  - 🥈 **Серебряная лига** — средний уровень
  - 🥉 **Бронзовая лига** — начальный уровень / новые команды
- **Между сезонами** — система повышения/понижения (promotion/relegation): например, топ-N команд Серебряной лиги поднимаются в Золотую, нижние N команд Золотой лиги опускаются в Серебряную, аналогично между Серебряной и Бронзовой. N настраивается администратором перед каждым сезоном.
- Новые команды, которые не участвовали ни в одном сезоне, стартуют в Бронзовой лиге (или в общей группе, если это всё ещё первый сезон платформы).

### 11.3 Годовой отбор на LAN-турнир

- По результатам всех официальных сезонов года копится **годовой командный рейтинг** (сумма очков/мест за все 3 официальных сезона, с весами — например, более поздние сезоны могут весить больше).
- В конце года лучшие команды по этому годовому рейтингу приглашаются на офлайн **LAN-турнир** с крупным призовым фондом — это "вершина" соревновательной пирамиды платформы и главный мотиватор для игроков на протяжении всего года.
- Нужен отдельный экран/страница "Путь на LAN" с текущим положением команды в годовом зачёте.

### 11.4 Новые сущности данных для этого модуля

```
Season
  id, name (напр. "Осень-зима 2026"), type (REGULAR / OFFSEASON_FUN),
  start_date, end_date, status (UPCOMING / REGISTRATION / ACTIVE / FINISHED),
  has_divisions (bool — false для первого сезона платформы)

Division
  id, season_id, name (GOLD / SILVER / BRONZE / NONE),
  tier_order (1=Gold, 2=Silver, 3=Bronze)

SeasonTeamEntry
  id, season_id, division_id (nullable для первого сезона), team_id,
  manager_id (-> User, кто заявил команду), points, matches_played,
  wins, draws, losses, goals_for, goals_against, final_position

PromotionRelegationRule
  id, season_id, division_id, promote_top_n, relegate_bottom_n

WeeklyCup
  id, week_start_date, status, is_scouting_flagged (bool — для команд, ищущих новичков)

AnnualStanding
  id, year, team_id, total_points_across_seasons, qualified_for_lan (bool)
```

### 11.5 Флоу: заявка команды на сезон

1. Менеджер (капитан) команды заходит в раздел "Мой клуб" → видит открытую регистрацию на предстоящий сезон (баннер/уведомление на главной странице и в паблике ВК-группы платформы — если есть).
2. Заявляет команду на сезон (создаётся `SeasonTeamEntry`), при необходимости оплачивает орг.взнос сезона (если платформа берёт плату за участие в сезоне, а не только с призовых).
3. Если сезон уже имеет дивизионы — команда автоматически ставится в дивизион по результатам прошлого сезона (или в Бронзу, если новая).
4. Формируется расписание тура (регулярные официальные матчи между всеми командами дивизиона — round robin в течение сезона, не единая elimination-сетка).
5. По окончании сезона — таблица дивизиона (`final_position` для каждой `SeasonTeamEntry`), применяется `PromotionRelegationRule`.

### 11.6 Как стать участником (для игрока, не менеджера)

1. Зарегистрироваться на сайте и **полностью заполнить профиль**: контактные данные, ссылки на соцсети, игровой ник (**геймертег должен точно совпадать** с тем, что указан в самой игре EA FC — иначе команда может получить санкции на официальном матче; нужна отдельная валидация/предупреждение в UI при заполнении профиля).
2. Далее у нового игрока два пути:
   - Уже быть игроком команды, которая участвует в текущем сезоне (тогда игрок автоматически считается участником через `TeamMember`).
   - Стать менеджером и заявить свою команду на сезон (флоу 11.5).
3. Рекомендуемый промежуточный шаг для новичков без команды — сыграть в открытых "сборных" матчах (все желающие собираются вместе через общий чат платформы), чтобы засветиться перед капитанами команд, которые ищут игроков.

## 12. Система рейтинга и статистики игроков (XP / Card Rating)

### 12.1 Ввод статистики матчей

После каждого сыгранного официального матча статистика по каждому игроку (точные передачи, обводки, выигранные единоборства и т.д.) вносится вручную специально назначенными сотрудниками платформы (роль **StatTracker** — расширение роли Moderator) через отдельную админ-форму ввода статистики матча. Обычно данные должны появляться в профиле игрока на следующий день после матча.

### 12.2 Формула XP

- XP — автоматически рассчитываемое значение на основе статистических показателей матча.
- Формула не публикуется пользователям (закрытый расчёт на backend), учитывает как позитивные, так и негативные игровые действия.
- **Формула индивидуальна для каждого игрового амплуа** (вратарь, защитник, полузащитник, нападающий — у каждого разный набор весов статистики, т.к. разные задачи на поле).
- К итоговому XP применяется **множитель дивизиона**: чем выше дивизион (Золотая > Серебряная > Бронзовая), тем выше множитель — это стимулирует бороться за место в топ-лиге.

#### 12.2.1 Производные метрики поверх базовых данных — альтернатива дорогому OCR

Полезная идея из практики похожего проекта (независимый разработчик статистической системы для лиги EA FC Clubs делился опытом: для него отправной точкой стало именно недовольство "голой" базовой статистикой при том, что EA не даёт нормального API). Его решение — не пытаться выцарапать из игры всё больше сырых метрик, а **считать собственные производные показатели поверх уже имеющихся базовых данных** (тех самых ~18-20 полей из EA API, раздел 12.7.1). Это даёт аналитическую глубину без необходимости городить OCR ради каждой новой метрики.

Примеры такого рода производных метрик (можно взять за основу для собственной формулы XP или как отдельные показатели в расширенной статистике игрока, раздел 15.2):

- **Пасов на голевую передачу (pXA)** — сколько передач в среднем делает игрок, чтобы создать голевой момент. Считается из уже имеющихся `passesmade`/`assists` (плюс `secondAssists`, если нужно учитывать и предголевые). Ниже значение — эффективнее игрок доводит мяч до опасной стадии; выше — больше "пустых" передач без реальной угрозы. Хорошо отличает "объёмных" плеймейкеров от реально результативных.
- **Beaten Rate (частота проигранных единоборств)** — доля проигранных оборонительных дуэлей от общего числа попыток. Считается из `tacklesmade`/`tackleattempts`, которые уже есть в базовых полях EA API. Особенно показательна для защитников и опорных полузащитников — там, где "успешные отборы" сами по себе мало что говорят о реальной надёжности игрока.
- **Коэффициент результативности ударов** — соотношение голов к ударам (`goals`/`shots`), показывает не только объём (много ли бьёт игрок), а именно эффективность завершения атак.

Такие метрики можно собирать в **композитные профили игрока** (например, радар-диаграмму по 4-6 осям, раздел 15.1) — это даёт пользователю быстрое визуальное понимание стиля и силы игрока без необходимости городить сложный видео-OCR пайплайн ради каждой новой метрики. Рекомендация: закладывать вычисление подобных производных показателей как отдельный, легко расширяемый слой поверх `PlayerCareerStat`/`PlayerTournamentStat` (раздел 15.5) — например `PlayerDerivedMetric` с полем `formula_key` и вычисленным значением, чтобы можно было добавлять новые производные метрики, не трогая основную схему сырых данных.

### 12.3 Пересчёт базового рейтинга карточки игрока

Правила пересчёта в начале нового сезона на основе **суммарного XP за предыдущий завершившийся официальный сезон**:

- Игроки ранжируются по суммарному XP за сезон → место в общем рейтинге определяет новый базовый рейтинг карточки.
- **Минимум 10 сыгранных официальных матчей за сезон**, чтобы попасть в пересчёт.
- Если матчей меньше 10 — рейтинг берётся из последнего сезона, где условие выполнялось, и уменьшается на **2 пункта**.
- Ограничение волатильности: новый базовый рейтинг не может отличаться от рейтинга прошлого зафиксированного сезона **больше чем на 5 пунктов** в любую сторону.

### 12.4 Бонусы к рейтингу в течение сезона

- **Команда тура (TOTW)** — по итогам каждого игрового тура формируется символическая сборная лучших игроков (по позициям). Попадание в TOTW даёт **+1** к текущему рейтингу карточки. Особое правило: если базовый рейтинг игрока ниже 75, первое попадание в TOTW сразу поднимает его до 75 (а не просто +1), последующие попадания добавляют по +1 как обычно.
- **Команда сезона (TOTS)** — по итогам всего сезона формируется символическая сборная сезона, попадание в неё даёт **+3** к рейтингу.

### 12.7 Автоматизация сбора статистики — три уровня, от простого к сложному

Есть три рабочих подхода к автоматизации, разной сложности разработки и разной надёжности. Рекомендуется реализовывать в порядке приоритета ниже — начиная с самого дешёвого по разработке и самого точного по данным, а видео-OCR оставить как резервный вариант на крайний случай.

#### 12.7.1 Основной способ — опрос неофициального Pro Clubs API EA

У EA существует **недокументированный, реверс-инженерный API** (домен `proclubs.ea.com/api/fc/...`), который используется множеством открытых community-инструментов (например npm-пакеты `proclubs-api`, `fc-clubs-api`, а также Discord-боты вроде OurProClub) — он отдаёт **готовый структурированный JSON**: историю матчей клуба, состав, и подробную статистику каждого игрока за матч (голы, ассисты, отборы, точность передач и т.д.) — то есть без всякого OCR.

**Как интегрировать:**

1. При создании клуба на платформе (раздел 13.1) добавляется дополнительное поле — **реальный EA Club ID + платформа** (PS / Xbox / PC), которое капитан указывает при регистрации клуба (аналогично тому, как игрок указывает геймертег в разделе 11.6).
2. Отдельный воркер (задача по расписанию через BullMQ, например каждые 15–30 минут в дни туров) опрашивает эндпоинт последних матчей для каждого клуба, участвующего в активном сезоне/турнире, и сравнивает с уже сохранёнными матчами в базе.
3. Когда находится новый матч из EA, которого ещё нет в базе — сверяется с запланированным `Match` (по времени проведения и паре клубов) и подтягивается подробная статистика по игрокам напрямую в `PlayerMatchStat`, без промежуточного видео и распознавания.
4. Логика сопоставления: матч из EA API привязывается к записи `Match` на платформе по совпадению пары клубов + окну времени вокруг `scheduled_at`. Если совпадений несколько (клубы сыграли несколько товарищеских подряд) — матч уходит на ручную сверку модератору, а не привязывается автоматически наугад.
5. Так как данные уже структурированы (не OCR, точность практически 100%), обязательный поштучный review можно ослабить до **выборочной проверки** (например, случайные 10% матчей или все матчи с аномальными значениями статистики), а не сверки каждого матча вручную, как в видео-варианте.

**Важные оговорки, которые нужно заложить в архитектуру:**

- Этот API **не публичный и не документированный официально EA** — доступ не гарантирован, может быть изменён, ограничен по частоте запросов или заблокирован в любой момент без предупреждения. Из обсуждений на форумах EA известно, что у EA есть отдельный "Direct Clubs API" с официальным доступом для избранных партнёров (например, для Virtual Pro Gaming) — по мере роста платформы имеет смысл попробовать подать заявку на официальный партнёрский доступ через EA, но это не гарантировано и не описано публично.
- **EA переиспользует числовые Club ID между версиями игры.** Подтверждено разработчиком популярного community-бота (OurProClub): при выходе новой версии игры (например FC25 → FC26) тот же самый Club ID может быть присвоен совершенно другому клубу. Пример из практики: клуб с ID 789 в FC26 — это один клуб, но как только в FC27 создаётся 789-й по счёту клуб, тот же ID начинает указывать уже на него, независимо от того, кто им реально владеет. **Это критично для `EAClubLink`** — нельзя один раз сохранить `ea_club_id` и полагаться на него бессрочно. Обязательно нужно хранить вместе с ID также версию/поколение игры (`game_version`, например "FC26"), периодически перепроверять, что `club_name` из ответа API всё ещё совпадает с ожидаемым названием клуба на платформе, и предупреждать/блокировать синхронизацию, если название разошлось — это защита от того, что платформа случайно начнёт подтягивать статистику чужого клуба.
- Будущее API в новых версиях игры (FC27 и далее) **не гарантировано** — по словам того же разработчика, EA не поддерживает Pro Clubs на консолях старого поколения в FC27, режим может быть серьёзно переработан, и неизвестно, сохранится ли структура API в текущем виде. Отсюда и рекомендация закладывать адаптер `StatsProvider` максимально изолированно (см. ниже).
- EA обычно хранит **ограниченную историю** последних матчей клуба — если опрос идёт слишком редко, старые матчи могут "вымыться" из истории раньше, чем их успеют забрать. Отсюда и рекомендация опрашивать чаще в дни туров.
- Архитектурно интеграцию стоит делать как **отдельный заменяемый адаптер** — интерфейс вида `StatsProvider.fetchClubMatches(clubId, platform)` / `fetchMatchPlayerStats(matchId)`, за которым скрыта конкретная реализация похода в EA API. Если эндпоинт изменится или отвалится — переписывается только этот слой, остальная система (обработка `PlayerMatchStat`, пересчёт XP) не затрагивается.
- **Готовая npm-библиотека под этот стек** — `eafc-clubs-api` (пакет `npm i eafc-clubs-api`, репозиторий `carlos-menezes/fc-clubs-api`), написана на TypeScript специально для режима Clubs. Даёт готовые методы: `searchClub()` (поиск клуба по имени), `overallStats()` (общая статистика клуба), `matchesStats()` (статистика всех матчей клуба), `memberCareerStats()`/`memberStats()` (статистика по каждому участнику клуба). Имеет смысл использовать её как отправную точку реализации адаптера `StatsProvider` вместо того, чтобы писать HTTP-запросы к EA с нуля — это экономит время на первой итерации Этапа 20. Библиотека написана под FC24 — при использовании стоит проверить актуальность полей/эндпоинтов под текущую версию игры (см. предупреждение выше про нестабильность API между версиями) и быть готовым, что для более новых версий (FC26 и далее) может понадобиться доработка или собственный форк.
- Именно поэтому видео-OCR пайплайн (12.7.3) не стоит выкидывать из плана полностью — держать его как резервный источник на случай, если официальный/неофициальный путь через EA станет недоступен.

**Точный список полей, реально приходящих от EA FC Pro Clubs API** (подтверждено официальной документацией community-бота OurProClub, актуально для FC26 — с новой версией игры список может измениться):

Данные о матче: `id`, `club_id`, `club_name`, `match_type` (leagueMatch / playoffMatch / friendlyMatch), `match_date` (timestamp), по каждому клубу — `goals`, `clubName`, `winnerByDnf` (флаг технического поражения при выходе соперника из матча).

Данные по каждому игроку (ключ — EA ID/геймертег): `mom` (лучший игрок матча), `pos` (goalkeeper/defender/midfielder/forward), `goals`, `saves` (только вратарь), `shots`, `rating`, `assists`, `secondAssists` (голевая на ассистента — предголевая передача), `dribbles` (успешные обводки), `redcards`, `passesmade`, `passattempts`, `archetypeid` (архетип игрока), `tacklesmade`, `tackleattempts`, `cleansheetsgk`, `cleansheetsdef`, `interceptions`, `secondsPlayed`.

Это **весь** набор — около 18-20 полей, что подтверждается и напрямую словами разработчика бота OurProClub: для FC26 EA отдаёт порядка 8 действительно значимых метрик на игрока (для сравнения — в API EA NHL их 50+). Все остальные, более гранулярные метрики (раздельные воздушные/наземные дуэли, провалы в штрафной, выносы, блоки ударов отдельной строкой и т.п., как на детализированных турнирных платформах) в этот список не входят и физически не приходят от EA — см. 12.7.1a ниже.

**Новая сущность данных:**

```
EAClubLink
  id, club_id (-> Club), ea_club_id, platform (PS / XBOX / PC),
  game_version (напр. "FC26" — критично из-за переиспользования ID между версиями игры, см. оговорки выше),
  last_verified_club_name (для сверки, что ea_club_id всё ещё указывает на нужный клуб),
  last_polled_at, last_synced_match_ea_id

EAApiMatchImport
  id, ea_match_id, matched_internal_match_id (-> Match, nullable),
  raw_json, import_status (IMPORTED / NEEDS_REVIEW / DISCARDED),
  imported_at
```

#### 12.7.1b Альтернативный/дополнительный источник — публичный API стороннего бота OurProClub

Отдельно от парсинга Discord-сообщений (12.7.2, который не даёт новых данных) у бота OurProClub есть **собственный публичный HTTP API**, отдающий JSON напрямую: `https://api.ourproclub.app/api/match/history?clubId={ea_club_id}&limit=500`. Это не более детальные данные, чем в 12.7.1 (та же ограниченная схема полей EA), но у него есть практическое преимущество: бот **сохраняет историю матчей у себя постоянно** (если в Discord-сервере клуба включена функция `/automode` или использовалась команда `/matches`), тогда как у самой EA глубина истории ограничена. Это может закрыть проблему "старые матчи вымылись из EA до того, как их успели забрать".

Использовать имеет смысл как **дополнительный/резервный** источник поверх 12.7.1, а не вместо него — зависимость от того, что конкретный клуб уже зарегистрирован в стороннем боте и включил сохранение истории, есть не всегда. Это стоит закладывать не в первую итерацию Этапа 20, а как расширение `StatsProvider` вторым провайдером в общем интерфейсе — если прямой опрос EA не находит нужный матч, система дополнительно проверяет этот резервный источник.

#### 12.7.1a Важно: EA API отдаёт ограниченный, но конкретный набор полей — не весь возможный список статистики

Это критично заложить в архитектуру с самого начала, чтобы не пытаться "выжать" из EA API данные, которых там нет, и не закладывать в UI поля, которые никогда не заполнятся автоматически.

**Подтверждённый набор полей на игрока за матч** (структура получена из документации сообщества, реверс-инжинирящего этот же EA API — см. 12.7.1b): `mom` (флаг "лучший игрок матча"), `pos` (укрупнённая позиция: goalkeeper/defender/midfielder/forward — **не детальное амплуа**), `goals`, `saves` (только для вратаря), `shots`, `rating`, `assists`, `dribbles` (успешные обводки), `redcards`, `passesmade`, `archetypeid` (ID игрового архетипа — можно использовать как доп. атрибут), `tacklesmade`, `passattempts`, `cleansheetsgk`, `interceptions`, `secondAssists` (**предголевая передача** — пас игроку, который отдал результативную передачу — вопреки более ранней оговорке в этом документе, это поле в API есть), `secondsPlayed`, `cleansheetsdef`, `tackleattempts`.

Это заметно больше, чем предполагалось раньше — прямой маппинг в `PlayerMatchStat` должен покрывать все эти поля один в один по названиям, чтобы не терять данные, которые EA реально отдаёт.

**Чего в этом наборе по-прежнему нет** и что реально требует ручного ввода/другого источника: детальное амплуа на конкретной позиции (ЛЗ/ЦЗ/ПЦЗ и т.п. — только грубая категория есть в API, детальную позицию нужно брать из профиля игрока на самой платформе, где он указывает предпочитаемые позиции), разбивка дуэлей по типам (в обороне/в атаке/в воздухе отдельно), блоки ударов, выносы, провалы в штрафной, точность навесов отдельно от обычных передач. Эти метрики остаются на ручном вводе StatTracker (раздел 12.1) либо на будущем видео-анализе (12.7.3).

**Как это должно быть устроено в модели данных** — важно понимать это ДО того, как проектировать таблицы/интерфейс матча, чтобы UI не "прыгал" между пустыми и заполненными колонками:

```
PlayerMatchStat  (обновление сущности из раздела 12.5)
  ...базовые поля (goals, assists, rating, shots, pass_accuracy, tackles,
      interceptions, cards, saves и т.д.) — заполняются автоматически
      из EA API (12.7.1) либо резервно из видео-OCR (12.7.3)...
  ...
  data_source (EA_API / VIDEO_OCR / MANUAL / DISCORD_BOT)
  has_extended_stats (bool) — true, если по этому матчу StatTracker
      дополнительно ввёл расширенные метрики поверх автоматических
  extended_stats (JSON, nullable) — гибкое поле для расширенных метрик
      (предголевые передачи, детальные дуэли и т.п.), которое заполняет
      только StatTracker вручную; UI показывает эти колонки только если
      has_extended_stats = true, а не пустыми прочерками для всех матчей
```

**Рекомендация по UI страницы матча**: сначала показывать базовый блок статистики (то, что гарантированно приходит из EA API — это должно работать для 100% матчей), а расширенный блок ("Детальная статистика") показывать отдельной раскрывающейся секцией/вкладкой, которая появляется только когда `has_extended_stats = true`. Так интерфейс не будет выглядеть "недогруженным" на матчах, где расширенной аналитики ещё нет — это осознанный дизайн, а не баг загрузки.

#### 12.7.1b Альтернативный/дополнительный источник — публичный API OurProClub

Помимо прямого похода в неофициальный EA API (12.7.1), у стороннего Discord-бота OurProClub есть **собственный публичный REST API** поверх сохранённой им истории матчей: `https://api.ourproclub.app/api/match/history?clubId={id}&limit={до 500}`. По структуре это тот же набор полей, что в 12.7.1a (бот сам берёт данные из EA API), но с важным отличием — **бот заранее копит и хранит историю матчей**, пока где-либо в его Discord-серверах активирован режим `/automode` или используется команда `/matches` для конкретного клуба.

**Чем это может быть удобнее прямого похода в EA:**

- Не нужно самостоятельно реверс-инжинирить недокументированный EA-эндпоинт с нуля — структура ответа уже задокументирована сообществом бота.
- Решает проблему ограниченной глубины истории у EA (см. 12.7.1) — если клуб уже давно использует бота, история матчей за прошлые недели/месяцы уже накоплена и доступна одним запросом, а не только "последние N матчей".

**Чем это хуже/рискованнее прямого похода в EA:**

- Полная зависимость от стороннего сервиса — по собственным словам разработчика бота, API доступен "пока бот онлайн", то есть при отключении/закрытии проекта OurProClub этот путь отвалится целиком, вне твоего контроля.
- Работает только для клубов, которые **уже зарегистрированы в этом конкретном боте** и явно включили сохранение истории (`/automode`/`/matches`) — то есть для новых клубов на твоей платформе это не будет работать "из коробки", придётся либо просить их подключить стороннего бота себе, либо всё равно параллельно иметь путь 12.7.1.
- Часть расширенных возможностей бота (например, точная агрегация карьерной статистики через команду `/career`) доступна только в платной Premium-подписке самого OurProClub — привязывать свой продукт к чужой платной подписке рискованно с точки зрения бизнеса.

**Рекомендация:** использовать как **опциональный дополнительный источник данных** через тот же адаптер `StatsProvider` (реализовать вторую реализацию интерфейса — `OurProClubStatsProvider` рядом с `DirectEaApiStatsProvider`), а не как основной путь. Основным считать 12.7.1 (прямой EA API), а OurProClub — быстрый способ сразу получить историческую глубину для клубов, которые уже туда переехали, либо как временный MVP на самом старте, пока не готова собственная прямая интеграция.

#### 12.7.1c Критичный риск на горизонте: неопределённость API для FC27

Важно учитывать при планировании обоих способов выше (12.7.1 и 12.7.1b) — они оба построены на одном и том же недокументированном EA API, а значит рискуют сломаться **одновременно**. Разработчик OurProClub прямо сообщает в своём Discord-сообществе: EA не оказывает поддержки разработчикам, использующим этот API, и с выходом FC27 (заявленная перестройка режима "Клубы" под форматы 2v2/3v3/5v5) неизвестно, сохранится ли текущая структура API вообще — для сравнения он приводит официальный, хорошо документированный API EA NHL с 50+ метриками на игрока против всего ~8–19 полей в текущем Pro Clubs API.

**Практический вывод для архитектуры платформы:**

- Паттерн адаптера `StatsProvider` (уже заложенный в 12.7.1) — не просто хорошая практика, а обязательное требование: при поломке/изменении EA API под FC27 должен переписываться только слой адаптера, а не логика начисления XP, профилей, рейтингов и всего остального продукта.
- Ручной ввод StatTracker (раздел 12.1) нельзя рассматривать как "временный костыль до полной автоматизации" — держать его в рабочем, поддерживаемом состоянии нужно постоянно, как гарантированный запасной путь на случай полного отказа обоих автоматических источников.
- Не стоит вкладывать чрезмерные ресурсы в глубокую автоматизацию (12.7 целиком) до того, как заработает и стабилизируется базовый ручной процесс — именно поэтому в дорожной карте (раздел 14/20) автоматизация идёт по приоритету и после того, как ручной ввод уже отлажен.

#### 12.7.1d Комбинирование источников: прямой EA API + OurProClub API одновременно

Это осмысленно делать **ради надёжности и полноты покрытия матчей**, но не ради расширения набора статистических полей — оба источника (12.7.1 и 12.7.1b) в конечном счёте читают один и тот же EA API, поэтому набор доступных метрик у них идентичен (см. 12.7.1a). Комбинирование не даёт детальную статистику вроде разбивки дуэлей или провалов в штрафной — это по-прежнему только через ручной ввод StatTracker (12.1).

**Рекомендуемая архитектура — цепочка провайдеров с приоритетом и сверкой:**

1. Реализовать оба провайдера под общим интерфейсом `StatsProvider` (`DirectEaApiStatsProvider` и `OurProClubStatsProvider`), которые уже заложены в 12.7.1 и 12.7.1b.
2. В сервисе синхронизации матчей вести список провайдеров в порядке приоритета (например: сперва прямой EA API как более "первичный" источник, затем OurProClub как источник с более глубокой историей).
3. Для каждого запланированного `Match`, ожидающего результат: опросить первый провайдер по списку; если матч не найден (например, ещё не сохранился/не успел появиться) — попробовать следующий провайдер по цепочке; если хотя бы один вернул данные — сохранить их как результат.
4. **Опциональная сверка (полезно, когда данные пришли из обоих источников)**: если по одному матчу удалось получить сырые данные из обоих провайдеров, сравнить построчно значения по игрокам. Полное совпадение — можно ослабить ручную проверку модератором до выборочной (см. 12.7.1). Расхождение хотя бы по одному значимому полю — принудительно помечать `NEEDS_REVIEW` вместо доверия любому из источников вслепую: расхождение чаще всего означает ошибку сопоставления матча (например, спутали два товарищеских подряд), а не то, что "один источник точнее другого".
5. Хранить в `EAApiMatchImport.data_source` не просто EA_API/OURPROCLUB_API, а фактически использованный провайдер по конкретному матчу — это нужно для отладки, если один из источников начнёт систематически давать сбои (сразу видно, какой).

**Обновление сущности данных:**

```
EAApiMatchImport  (обновление сущности из раздела 12.7.1)
  ...
  data_source (DIRECT_EA_API / OURPROCLUB_API)
  cross_validated (bool) — true, если удалось сверить с другим провайдером
  cross_validation_mismatch (bool) — true, если сверка выявила расхождение
```

#### 12.7.2 Дополнительно — уведомления через стороннего Discord-бота

Подробный разбор публичного API OurProClub как источника данных вынесен в 12.7.1b выше (это не отдельный уровень автоматизации, а вариант реализации того же уровня 12.7.1 — данные там из того же EA API). Отдельно от получения данных, такого бота можно использовать чисто для UX: автоматически публиковать в чат клуба готовый результат матча, который платформа уже получила через 12.7.1/12.7.1b, в удобном для игроков формате — это дополнение, не источник новой статистики.

#### 12.7.3 Резервный способ — видео + Computer Vision/OCR

Самый трудоёмкий, но и самый независимый от внешних сервисов вариант — на случай, если оба способа выше окажутся недоступны (EA заблокировала API, сторонний бот перестал работать и т.п.), либо для турниров/матчей, не попадающих в историю EA.

**Альтернатива классическому OpenCV+Tesseract пайплайну — распознавание через мультимодальную LLM.** Есть открытые проекты (например, извлечение статистики из скриншотов Pro Clubs через Google Gemini API), которые вместо жёсткой сетки ROI-координат и отдельного OCR-движка просто отправляют кадр целиком в vision-модель (Gemini / GPT-4V / Claude) с промптом вида "извлеки статистику каждого игрока с этого скриншота в JSON по такой-то схеме". Это значительно проще в реализации и устойчивее к изменению интерфейса между версиями игры или разными разрешениями видео — не нужно поддерживать конфиги координат под каждое разрешение и вкладку (12.7.3.1). Компромисс — это платные запросы за каждое изображение (хотя у Gemini есть бесплатный тир через Google AI Studio) и небольшой риск, что модель может неточно "додумать" число при плохом качестве кадра, поэтому для чисел, критичных для расчёта XP/призовых, всё равно стоит оставлять шаг верификации модератором (см. основной флоу 12.7, пункт 4). На практике для MVP можно комбинировать: дедупликация кадров по 12.7.3.2 (чтобы не гонять LLM на каждый повторяющийся кадр, а только на уникальные "экран игрока + вкладка"), и на каждый такой уникальный кадр — один вызов vision-LLM вместо связки ROI+Tesseract. Это резко сокращает объём кода и количество мест, которые могут сломаться при малейшем изменении интерфейса игры.

##### 12.7.3.0 Наблюдения по реальной записи экрана (важно учесть в реализации)

По тестовой записи экрана статистики матча EA FC подтвердились несколько важных деталей, которые меняют детали реализации 12.7.3.1–12.7.3.2:

1. **Расширенные метрики реально показываются самой игрой**, просто не отдаются через API из 12.7.1. На экране статистики отдельного игрока (вкладка «Защита» и другие) видны именно те детализированные показатели, которых нет в сыром EA API: "Дуэли в нападении" / "Дуэли в обороне" раздельно, "Процент выигранных дуэлей в нападении/обороне", "Воздушные дуэли" и "Процент выигранных воздушных дуэлей", "Обыгрыши соперником", "Провалы в оборонительной трети поля", "Провалы в штрафной" и т.д. Это подтверждает, что видео-OCR — единственный рабочий путь получить эти метрики автоматически (раз в API их нет, а вручную вводить долго).
2. **У экрана статистики игрока — два независимых направления скролла**, и дедупликацию (12.7.3.2) нужно строить с учётом обоих:
   - по вертикали **слева** — прокручивается список игроков команды, меняется выделенная (активная) строка;
   - по вертикали **справа** — прокручивается сама панель метрик выбранного игрока (там больше строк показателей, чем помещается на экране, поэтому нижние появляются по мере скролла).

   Значит, буфер `currentPlayerBuffer` из 12.7.3.2 должен закрываться (флашиться) не только при смене никнейма слева, но и при смене вкладки статистики (Сводка/Владение/Удары/Передачи/Защита/Вратарь) — а накопление внутри одного игрока и одной вкладки должно идти по мере скролла правой панели, а не одним кадром.

3. **Никнейм для сопоставления с аккаунтом на платформе нужно брать строго из левого списка**, а не из крупного заголовка над панелью метрик. Крупный заголовок показывает **имя созданного в игре "Про"-персонажа** (например может отображаться "Javier Zanetti"), которое игрок задаёт себе сам при создании виртуального футболиста, и оно может вообще не совпадать с его геймертегом/ником на платформе. OCR должен читать именно колонку списка слева — она соответствует геймертегу, который и хранится в `GamertagHistory` (раздел 15.1).
4. **Мини-схема поля под панелью метрик — это не расстановка команды**, а тепловая карта конкретного игрового действия выбранного игрока (например "Отборы ИИ" — точки, где игрок совершал отборы за матч), с переключателем влево/вправо, судя по всему, между несколькими типами карт действий для этой вкладки. Это отдельная от 12.7.3.3 (экран расстановки всей команды) фича — те же приёмы (поиск зелёного поля, перевод координат точек в проценты) можно переиспользовать, но данные разные: здесь координаты точек действий одного игрока, не позиции всех игроков команды. В MVP можно не реализовывать сбор этих тепловых карт — они не обязательны для расчёта XP/рейтинга (раздел 12.2–12.3) и являются, скорее, дополнительной визуализацией на будущее.

##### 12.7.3.1 Жёсткая сетка координат (ROI) по вкладкам статистики

Интерфейс EA FC статичен и не меняет пропорции в рамках одного разрешения видео — поэтому не нужно сканировать весь кадр целиком, достаточно заранее заданной маски координат под каждую известную зону.

- Экран статистики после матча имеет несколько вкладок (Сводка / Владение / Удары / Передачи / Защита / Вратарь / Другое — как видно на разделе статистики профиля, раздел 15.2). Каждая вкладка имеет свой фиксированный набор колонок в фиксированных пиксельных координатах.
- Конфиг ROI должен быть организован как словарь **разрешение → вкладка → зоны**:
  ```
  roiConfig = {
    "1920x1080": {
      "summary":    { playerListArea: {x,y,w,h}, columns: [{key:"rating", x,y,w,h}, ...] },
      "shooting":   { playerListArea: {x,y,w,h}, columns: [{key:"xg", x,y,w,h}, {key:"shots_on_target", x,y,w,h}, ...] },
      "passing":    { ... },
      "defending":  { ... },
      "goalkeeping":{ ... }
    },
    "1280x720": { ... }
  }
  ```
- Так как в самом видео игрок может листать вкладки статистики (не только прокручивать список игроков), скрипту нужно на каждом кадре сначала определить, **какая вкладка сейчас активна** — либо через OCR текста заголовка вкладки, либо через template matching иконки вкладки (иконка — это маленькая, стабильная по пикселям картинка, matchTemplate из OpenCV справится быстрее и надёжнее, чем гонять OCR по всему заголовку каждый кадр) — и уже по результату выбирать нужный набор ROI из конфига.
- Матч может быть снят в разных разрешениях (1920×1080, 1280×720 и т.д.) — конфиг обязательно должен быть параметризован по разрешению исходного видео, а не жёстко зашит под одно.

##### 12.7.3.2 Склейка строк и дедупликация при прокрутке

Так как таблица/карточки игроков в видео прокручиваются плавно, один и тот же игрок и его показатели будут видны на нескольких кадрах подряд — наивный сбор данных по каждому кадру приведёт к дублям.

Алгоритм (с учётом двух осей скролла из 12.7.3.0):

1. На каждом кадре из зоны списка игроков (левая колонка) через OCR читается никнейм текущей активной/выделенной строки — **именно эта колонка**, а не крупный заголовок над правой панелью (см. 12.7.3.0, пункт 3).
2. Дополнительно определяется активная вкладка статистики (Сводка/Владение/Удары/Передачи/Защита/Вратарь) — см. 12.7.3.1.
3. Скрипт ведёт в памяти буфер `currentPlayerBuffer`, ключ которого — пара `(nickname, activeTab)`. Пока и никнейм, и вкладка не меняются — новые прочитанные значения из правой панели (которая сама может прокручиваться вертикально, показывая новые строки метрик) добавляются в буфер, **если такой метрики там ещё нет** (сравнение по ключу метрики, а не по всему кадру).
4. Буфер сохраняется (флашится) в промежуточную структуру при смене **любого** из двух параметров ключа — никнейма слева или активной вкладки справа — а не только при смене никнейма.
5. В конце обработки видео все буферы по всем игрокам и всем вкладкам сливаются в единый JSON по матчу и передаются на этап сопоставления игроков (см. основной флоу 12.7 выше).

##### 12.7.3.3 Парсинг экрана расстановки (схема поля)

Отдельная, самостоятельная под-задача: EA показывает после матча экран расстановки — цветные кружки-иконки игроков на зелёном поле, где внутри кружка виден рейтинг за матч, а под кружком — никнейм. Эти данные нужны, чтобы автоматически заполнять визуализацию "Позиционный рейтинг" (раздел 15.1) и общую схему матча, а не рисовать её вручную.

Пайплайн для этого экрана:

1. **Поиск зелёного поля** — цветовая маска (HSV-диапазон зелёного) находит прямоугольную область поля в кадре, её границы становятся системой координат (0–100% по X и Y) для дальнейшего пересчёта.
2. **Поиск кружков-иконок игроков** — либо через `cv2.HoughCircles` (поиск окружностей), либо через цветовую маску по двум характерным цветам команд (например, оранжевый/синий, как видно на референс-скрине), что обычно надёжнее и быстрее, чем HoughCircles на реальных кадрах с шумом/сжатием видео.
3. **Определение команды** — по доминирующему цвету найденного кружка (оранжевый/синий и т.п.) автоматически определяется, какой из двух клубов представляет игрок — не нужно спрашивать пользователя.
4. **OCR рейтинга внутри кружка** — небольшая ROI-зона внутри каждого найденного круга, число обычно крупное и контрастное — должно распознаваться с высокой точностью даже базовым OCR.
5. **OCR никнейма под кружком** — ROI чуть ниже центра каждого круга.
6. **Пересчёт координат в проценты** — центр каждого найденного круга переводится из абсолютных пикселей кадра в проценты относительно границ зелёного поля, найденных на шаге 1 (`pos_x_percent = (circle_x - field_left) / field_width * 100`, аналогично по Y). Именно проценты, а не пиксели, сохраняются в БД — тогда фронтенд может отрисовать те же точки поверх CSS-поля любого размера на любом экране.
7. Результат — массив объектов `{nickname, rating, team_id, pos_x_percent, pos_y_percent}` на весь матч, который дальше сшивается с уже собранной статистикой (12.7.3.2) по никнейму.

**Новая сущность данных:**

```
MatchFormationSnapshot
  id, match_id, extracted_at,
  players (JSON — массив {nickname, rating, team_id, pos_x_percent, pos_y_percent})
```

Эти данные используются как основа для визуализации на странице матча (аналог блока с рейтингами игроков на поле, как в референс-интерфейсе) и для накопления истории позиций игрока — которая со временем и формирует блок "Позиционный рейтинг" в профиле (раздел 15.1), автоматически, без ручного заполнения.

**Пайплайн обработки:**

1. **Загрузка видео.** Два источника, оба ведут к одному внутреннему API:
   - через сайт — форма "Загрузить статистику матча" на странице матча, файл сразу уходит в object storage (Cloudflare R2/S3);
   - через Discord-бота — отдельный лёгкий сервис на `discord.js` в специальном канале скачивает присланное видео, кладёт в тот же storage и дёргает internal API `/matches/:id/extract-stats` с URL видео.
   - В обоих случаях создаётся запись `MatchStatExtractionJob` со статусом `QUEUED`.

2. **Обработка — отдельный worker-сервис** (не основной веб-процесс API!), слушающий очередь BullMQ:
   - **Извлечение кадров** — `fluent-ffmpeg` (Node-обёртка над ffmpeg) разбивает видео на кадры, 1–2 кадра в секунду достаточно, чтобы не пропустить прокручиваемую статистику.
   - **Обрезка зон интереса (ROI)** — через `sharp` вырезаются фиксированные прямоугольники координат: интерфейс EA FC стандартизирован, поэтому координаты зоны "список игроков" (для определения, кто сейчас выделен/активен) и зоны "значения статистики" известны заранее (нужен конфиг координат под каждое типовое разрешение видео — 1920×1080, 1280×720 и т.д., т.к. игроки присылают видео в разном разрешении).
   - **Предобработка кадра** — приведение к чёрно-белому, увеличение контраста (тоже через `sharp`) для повышения точности OCR.
   - **Распознавание текста (OCR)**:
     - MVP-вариант — `tesseract.js` (open-source, бесплатно, работает прямо в Node);
     - продакшн-вариант с высокой точностью, особенно для кириллицы — облачный API (`@google-cloud/vision` или Yandex Vision), платный за объём.
     - Рекомендуемая стратегия: начать с Tesseract.js, а для кадров с низким confidence score распознавания — автоматически пересылать их в облачный API как fallback (гибрид: дёшево на основной массе, точно на сложных случаях).
   - **Сборка и дедупликация** — по последовательности кадров скрипт определяет, какой игрок сейчас выделен в списке слева, собирает пары "метрика → значение" из правой зоны, игнорирует уже собранные повторяющиеся значения (статистика видна на нескольких соседних кадрах, пока прокрутка на одном игроке). При смене выделенного игрока — сохраняет собранный JSON предыдущего игрока и начинает собирать для следующего.
   - Итог этапа — структурированный JSON статистики по каждому игроку матча.

3. **Сопоставление с игроками.** Распознанный никнейм сверяется с `GamertagHistory`/текущими геймертегами именно тех игроков, что заявлены на этот матч (через `TournamentParticipant`/состав команд), а не со всей базой пользователей — это резко снижает риск ложных совпадений. Дополнительно — fuzzy-matching (например, расстояние Левенштейна) на случай, если OCR ошибся в 1–2 символах ника.

4. **Обязательная верификация перед публикацией** (критично для доверия к системе — полностью автоматическая публикация без проверки недопустима):
   - Распознанные данные не попадают в профиль игрока сразу — job переходит в статус `AWAITING_REVIEW`.
   - StatTracker в админке видит таблицу: распознанные значения + confidence score OCR + оригинальный кадр рядом для визуальной сверки.
   - Модератор одним кликом подтверждает всю пачку целиком либо точечно правит отдельные неверно распознанные значения — это на порядок быстрее, чем вводить всё вручную с нуля.
   - После подтверждения создаются записи `PlayerMatchStat`, запускается пересчёт XP (раздел 12.2).

5. **Самообучение со временем (после MVP, опционально).** Каждое ручное исправление модератора — готовая пара "распознано автоматически / верное значение". Накопленный датасет можно использовать для дообучения собственной OCR-модели под конкретный шрифт интерфейса EA FC, постепенно снижая долю ручных правок.

**Новые сущности данных:**

```
MatchStatExtractionJob
  id, match_id, source (WEB_UPLOAD / DISCORD_BOT), video_url,
  status (QUEUED / PROCESSING / AWAITING_REVIEW / APPROVED / FAILED),
  raw_extracted_json (JSON — сырые данные по каждому игроку),
  overall_confidence_score, processed_at, reviewed_by (-> StatTracker), reviewed_at

ExtractionFrameSample  (опционально, для отладки и накопления датасета под 12.7.5)
  id, job_id, frame_timestamp_ms, roi_type (PLAYER_LIST / STAT_VALUE),
  cropped_image_url, ocr_raw_text, ocr_confidence
```

**Технические заметки:**

- Обработку видео нельзя гонять в основном процессе NestJS API — обязателен отдельный worker-процесс (можно в том же проекте, но отдельная точка входа, слушающая BullMQ-очередь), иначе тяжёлая обработка положит основной API под нагрузкой.
- Ключевые библиотеки: `fluent-ffmpeg`, `sharp`, `tesseract.js`, опционально `@google-cloud/vision`. Для поиска кругов/цветовых масок на схеме поля (12.7.3.3) понадобится полноценный OpenCV — в Node-экосистеме для этого обычно вызывают Python-скрипт как отдельный шаг пайплайна (через `child_process`) с `opencv-python`, либо используют `opencv4nodejs` — на практике первый вариант проще в поддержке.
- Видео-пайплайн остаётся **резервным** источником данных — основной путь для MVP автоматизации это 12.7.1 (прямой опрос EA API), он на порядок дешевле в разработке и точнее по данным. Раздел 12.7.3.3 (расстановка на поле) при этом полезен независимо от выбора основного источника статистики — EA API не отдаёт координаты расстановки, только текстовые метрики, так что визуализацию позиций в любом случае придётся либо парсить с видео, либо оставлять без неё на первых порах.
- Ручной ввод StatTracker'ом (раздел 12.1) в любом случае остаётся конечным резервом на случай сбоя всех трёх автоматических способов.

## 13. Клубы, трансферы и контракты

### 13.1 Создание клуба

Отдельная страница/форма «Создать клуб» со следующими полями и блоками:

**Основные данные:**

- Название клуба (обязательное)
- Сокращение (короткий тег клуба, обязательное — используется в таблицах, сетках, где мало места)
- Страна (выпадающий список)
- Группа во ВКонтакте (URL, опционально)
- Канал на Twitch (URL, опционально)
- Канал на YouTube (URL, опционально)

**Цветовая схема клуба:**

- Основной цвет — выбор из палитры свотчей (заготовленный набор ~10-12 цветов)
- Второй цвет — аналогичный выбор из палитры
- Акцентный цвет — «необязательный цвет для воротника, номеров и акцентов» — тоже выбор из палитры

**Шаблон формы (генератор игровой футболки):**

- Галерея из 8 готовых шаблонов дизайна формы (например: классический, вертикальные полосы, полоса на груди, диагональ, контрастные рукава, центральная полоса, половинки, геометрический узор)
- Live-превью выбранной формы тут же перерисовывается в цветах, выбранных выше (основной/второй/акцентный) — это SVG- или Canvas-генератор, а не загрузка готовой картинки
- Подпись под превью: «Так форма будет выглядеть в сборной тура и других клубных блоках» — то есть эта сгенерированная форма переиспользуется как визуальный идентификатор клуба в других местах платформы (например, иконка в TOTW/TOTS)

**Персонализация (шапка страницы клуба):**

- Превью «как на странице клуба» — широкий баннер-шапка (аналог cover-фото), можно загрузить свою картинку
- Рекомендации по размеру: ориентировочно 1890×320 px (соотношение сторон примерно 189:32), максимальный размер файла — до 1 МБ
- Кнопка "Выберите изображение" / "Загрузить обложку"

**Сохранение:**

- Кнопка "Сохранить" создаёт клуб; создатель автоматически становится менеджером/капитаном (`TeamMember.role = captain`).
- Логотип клуба отдельно от баннера — **рекомендуется формат PNG без прозрачного фона** (нужна валидация на фронте/бэке — проверка альфа-канала при загрузке), т.к. логотип используется как маленькая иконка на разноцветных фонах по всему сайту (таблицы, сетки турниров, карточки матчей).

### 13.1.1 Дополнительные сущности данных для формы создания клуба

```
Club (расширение сущности Team из раздела 3)
  ...существующие поля Team...
  abbreviation, country, vk_group_url, twitch_url, youtube_url,
  primary_color (hex), secondary_color (hex), accent_color (hex, nullable),
  kit_template_id (-> KitTemplate), cover_banner_url

KitTemplate
  id, name (напр. "Классический", "Вертикальные полосы", "Полоса на груди",
       "Диагональ", "Контрастные рукава", "Центральная полоса",
       "Половинки", "Геометрический узор"),
  render_type (SVG_LAYERED / CANVAS_GENERATED),
  template_asset_url  (базовый SVG/шаблон, куда программно подставляются
       primary_color / secondary_color / accent_color клуба)
```

Технически генератор формы проще всего реализовать как набор SVG-файлов с именованными `<path>`-слоями (например `body-primary`, `sleeves-secondary`, `collar-accent`), где цвет каждого слоя задаётся через CSS `fill` на основе `primary_color`/`secondary_color`/`accent_color` клуба — тогда превью перекрашивается мгновенно на фронтенде без бэкенд-рендеринга картинки.

### 13.2 Раздел "Трансферы"

Два подраздела:

- **Игроки ищут команду** — игрок публикует объявление: амплуа, игровые дни/время, короткое "о себе". (`PlayerTransferAd`)
- **Клубы ищут игроков** — капитан публикует открытую вакансию клуба: нужное амплуа, требования, условия. (`ClubTransferAd`)

Игроки и капитаны находят друг друга через эти списки и связываются напрямую (через контакты в профиле или встроенный чат/сообщения, если будет реализован).

### 13.3 Контракты

- Капитан отправляет игроку предложение контракта через "Мой клуб": срок действия (**максимум 3 месяца**), сумма отступных (buyout fee) за досрочный уход.
- Игрок получает список предложенных контрактов в своём кабинете и принимает/отклоняет.
- **Если у контракта указан срок действия — игрок не может самостоятельно покинуть клуб до его истечения без согласия капитана** (либо выплатив отступные, если такая опция предусмотрена).
- По истечении срока контракт автоматически становится "открытым" (free agent), либо продлевается, если обе стороны подтвердили продление.

### 13.4 Новые сущности данных

```
PlayerTransferAd
  id, user_id, position, available_days (JSON), about_text,
  status (ACTIVE / CLOSED), created_at

ClubTransferAd
  id, team_id, position_needed, requirements_text,
  status (ACTIVE / CLOSED), created_at

Contract
  id, team_id, user_id, offered_by (-> captain User),
  duration_months (max 3), buyout_fee,
  status (PENDING / ACCEPTED / DECLINED / ACTIVE / EXPIRED / TERMINATED),
  start_date, end_date, created_at
```

## 15. Детальная спецификация страницы профиля игрока

Профиль игрока — один из самых насыщенных экранов платформы, состоит из 4 вкладок.

### 15.1 Вкладка «Профиль»

- **Карточка игрока** (виджет в стиле FUT-карточки): крупный рейтинг + сокращение амплуа сверху, фото/аватар, ник игрока, набор из 6 характеристик (аналог атаки/паса/дриблинга/созидания/обороны/единоборств — можно адаптировать под свой набор метрик), флаг страны, логотип текущего клуба. Кнопки: "Как считается рейтинг" (ссылка на FAQ), "Скачать" (карточку как картинку — полезно для игроков, чтобы делиться в соцсетях).
- **Блок личных данных**: дата регистрации на платформе, игровой ник (должен совпадать с ником в самой игре — см. 11.6), ФИО (опционально), страна, город, дата рождения/возраст, статус подписки (если будет премиум), основное амплуа, дополнительные амплуа, иконки-ссылки на соцсети игрока.
- **Блок «Условия контракта»**: текущий клуб, статус игрока (игрок / капитан / менеджер), дата окончания контракта (или "бессрочно"), сумма отступных, кнопка "Подробная информация" → модалка/страница с полной историей контракта.
- **Блок «Избранные награды»** — игрок может закрепить несколько наград из своей коллекции трофеев на видном месте профиля (пустое состояние: "Нет избранных наград").
- **Блок «Общая статистика»** — агрегированные показатели за всё время на платформе: всего сыграно матчей, всего заработано XP, средний рейтинг, голы, голевые передачи, точность передач (%), успешные отборы, перехваты, сухие матчи (для вратарей). У каждой метрики — глобальный ранк игрока среди всех пользователей платформы (например "#1344"), что создаёт соревновательный элемент и мотивацию улучшать статистику.
- **Блок «Любимые позиции»** — горизонтальные полоски с процентом времени, проведённого на каждой позиции (вратарь / центр. защ. / фланг. защ. / опорн. полузащ. / центр. полузащ. / фланг. полузащ. / атак. полузащ. / нападающий).
- **Блок «Позиционный рейтинг»** — визуализация футбольного поля с расстановкой игрока по позициям, где он играл; на каждой позиции отображается средний рейтинг именно за матчи на ней (например, ЦЗ 7.25, ЛЗ 7.19 и т.д.) — наглядно показывает, где игрок сильнее всего.
- **История смены геймертега** — список всех прошлых игровых ников с датами действия (важно для модерации/детекта смены личности и споров).

### 15.2 Вкладка «Статистика»

Три под-вкладки:

- **Турнирная** — построчно статистика по каждому турниру/сезону, в котором участвовал игрок.
- **Клубная** — статистика в разрезе клубов, за которые он выступал.
- **В матчах** — статистика по каждому отдельно сыгранному матчу.

Фильтры над таблицей:

- **По амплуа** — просмотр статистики только за матчи на конкретной позиции (Все / ЦАП / КЗ / К3 / ФЛ / КП и т.п. — набор сокращений своих позиций).
- **По категории метрик** — переключатель: Общая сводка / Удары / Пасы / Перемещение / Отбор мяча / Выбор позиции / Удержание мяча / Другие / Вратарские (отдельный набор метрик для голкиперов).

Столбцы таблицы (турнирная вкладка): название турнира/сезона (ссылка + иконка лиги), заработано XP, средний рейтинг за турнир, сыграно матчей, голы, голевые передачи, гол+пас суммарно, показатель импакта на результат (+/-), сейвы (вратари), перехваты, % побед, % выигранных единоборств.

### 15.3 Вкладка «Переходы»

Таблица истории трансферов игрока между клубами: клуб (с логотипом), количество матчей, сыгранных в составе клуба, средний рейтинг за этот период, оценка капитана в звёздах (если реализована такая механика), сколько дней провёл в клубе, период пребывания (дата входа → дата ухода, с визуальными стрелками "вошёл"/"вышел").

### 15.4 Вкладка «Трофеи»

Фильтр по категориям наград:

- Все награды
- Командные достижения (медали за результаты команды — золото/серебро/бронза лиги, кубков)
- Индивидуальные достижения (личные награды — MVP тура, лучший бомбардир и т.п.)
- Руководство (награды за менеджерскую/капитанскую деятельность)
- Еженедельный кубок (награды за результаты в регулярном пятничном турнире)
- Символические клубы (за попадания в TOTW/TOTS)
- Особые (уникальные разовые/праздничные награды)

Каждая награда отображается карточкой: иконка, название, короткое описание условия получения, ссылка "Подробнее" (модалка с деталями — когда и за что именно получена).

## 16. Важное юридическое примечание

Приём платежей за участие в турнирах с призовым фондом регулируется в разных странах по-разному (законы об азартных играх могут применяться в зависимости от того, считается ли результат skill-based или game-of-chance). Перед реальным запуском с реальными деньгами — обязательна консультация с юристом в юрисдикциях, где планируется работать. Этот документ не является юридической консультацией.
